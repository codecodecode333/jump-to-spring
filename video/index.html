점프 투 스프링부트, 한 번쯤 따라 해 보셨죠?
저도 책대로 질문답변 게시판을 끝까지 만들고, 한 커밋씩 고쳐 나갔습니다.
오늘은 그중 일곱 가지를 보여 드립니다.
URL, 엔티티, N+1 문제, 보안, 테스트, 폼, 패키지 구조입니다.
각 장은 교재 방식, 문제점, 개선 코드, 결과 증명 순서로 갑니다.
범위는 교재 2장 컨트롤러부터 3장 검색까지입니다.
개선 아이디어는 장희성 강사님의 14163, 14168 강의에서 가져왔습니다.
환경은 Spring Boot 4.1.2, Java 25입니다.
교재는 Boot 3 기준이라 그대로 치면 막히는 곳도 있습니다.
교재 구현까지 커밋 서른여섯 개, 테스트 쉰일곱 개입니다.
커밋마다 무엇을, 왜, 어떻게 확인했는지 README에 남겼습니다.
첫 번째, URL 설계입니다.
교재는 question/detail/5, answer/create처럼 주소에 동사가 들어갑니다.
무엇을 할지는 HTTP 메서드가 이미 말해 주는데, 주소가 한 번 더 말하는 거죠.
게다가 삭제가 GET 링크입니다. 이건 보안 장에서 다시 봅니다.
그래서 주소는 자원, 행위는 메서드로 나눴습니다.
조회는 GET /questions/5, 수정은 PUT, 삭제는 DELETE입니다.
답변은 질문에 딸린 자원이라 POST /questions/5/answers입니다.
그런데 HTML 폼은 GET과 POST만 보낼 수 있습니다.
그래서 hiddenmethod 필터를 켰습니다.
th:method="put"이라고 쓰면 숨은 필드 _method가 함께 만들어지고,
서버의 필터가 이 값을 보고 요청을 PUT으로 바꿉니다.
삭제 링크는 global.js가 같은 일을 합니다.
a 태그에 method 속성만 붙이면 DELETE로 보냅니다.
실제로 질문을 수정하면 PUT으로 처리되고, 수정 시각이 표시됩니다.
두 번째, 엔티티 설계입니다.
교재의 엔티티는 모든 필드에 Setter가 열려 있습니다.
답변 하나를 만들 때도 setter를 네 번 부르고 save합니다.
작성일은 직접 넣고, 다대일 관계는 즉시 로딩입니다.
누구나 아무 데서나 값을 바꿀 수 있어서 실수가 생기기 쉽습니다.
그래서 여섯 가지를 고쳤습니다.
첫째, BaseEntity에 id, 생성일, 수정일을 모으고,
날짜는 JPA Auditing이 자동으로 채웁니다.
둘째, Setter를 없애고 기본 생성자는 protected로 막았습니다.
셋째, 답변은 question.addAnswer()로만 만듭니다.
양쪽 관계가 한 번에 맞춰지고, cascade로 저장됩니다.
넷째, 다대일 관계는 모두 LAZY로 바꿨습니다.
다섯째, orphanRemoval로 목록에서 빼면 DB에서도 삭제됩니다.
여섯째, equals와 hashCode입니다.
LAZY는 프록시를 줄 수 있어 getClass 비교는 틀릴 수 있습니다.
그래서 Hibernate.getClass로 실제 클래스를 비교합니다.
리포지터리 테스트 열한 개로, 이 동작들이 실제 SQL로 실행되는지 확인했습니다.
세 번째, N+1 문제입니다.
교재 3장은 목록 제목 옆에 답변 개수를 보여 줍니다. 코드는 한 줄이죠.
그런데 이 한 줄이 쿼리를 몇 번 실행할까요?
질문 열 개 조회 한 번, 전체 개수 한 번,
그리고 질문마다 답변 조회가 따로, 열 번 나갑니다.
목록 한 페이지에 SQL이 열두 번입니다.
질문 수만큼 쿼리가 늘어나서 N+1 문제라고 부릅니다.
해결은 설정 한 줄, default_batch_fetch_size: 100입니다.
이제 답변을 IN 절로 한 번에 묶어서 가져옵니다.
엔티티 코드는 하나도 바꾸지 않았습니다.
줄었는지는 테스트로 증명했습니다.
하이버네이트 통계로 쿼리 수를 세서, 세 번 이하면 통과합니다.
설정을 일부러 빼고 돌리면, 열두 번으로 실패합니다.
설정의 효과를 실패하는 테스트로 확인한 겁니다.
네 번째, 보안입니다. 교재 코드의 구멍 세 가지를 막았습니다.
첫째, 상태를 바꾸는 GET 요청입니다.
교재는 삭제와 추천을 GET으로 보내고, 로그아웃도 GET을 허용합니다.
GET은 다른 사이트의 이미지 태그 하나로도 보낼 수 있습니다.
그래서 이런 요청은 모두 POST, PUT, DELETE로 바꾸고,
CSRF 토큰이 있어야만 처리되게 했습니다.
토큰 없이 보내면 403으로 거절되는 것도 테스트로 고정했습니다.
둘째, 상태 코드입니다. 교재는 남의 글을 고치려 하면 400을 돌려줍니다.
400은 요청 형식이 잘못됐다는 뜻이죠. 이건 권한 문제라 403이 맞습니다.
글쓴이 확인은 엔티티의 isAuthor 메서드로 옮겼습니다.
셋째, 가장 중요한 마크다운 XSS입니다.
교재의 마크다운 변환은 기본 설정이라 본문의 HTML이 그대로 출력됩니다.
본문에 script 태그를 넣으면, 글을 여는 모든 사람의 브라우저에서 실행됩니다.
그래서 escapeHtml과 sanitizeUrls 옵션을 켰습니다.
같은 입력을 넣어 보면, 교재 방식은 script가 그대로,
개선 방식은 글자로 바뀌어 나옵니다.
